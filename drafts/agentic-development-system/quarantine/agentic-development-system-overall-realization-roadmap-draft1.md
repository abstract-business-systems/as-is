# Agentic Development System — Overall Realization Roadmap
Purpose: Provide a human-facing, program-wide sequence for realizing the accepted draft-11 architecture without authorizing execution or narrowing the program to its first pilot.

## Status and authority

This roadmap is a planning artifact derived from the human-accepted draft-11 target envelope. It explains how that envelope could be realized, evaluated, migrated, and eventually proposed for adoption.

**This roadmap authorizes no task, kick-off, implementation, benchmark, target adoption, commit, merge, artifact retirement, external effect, or worker launch.** Every executable unit still requires its own applicable Human Review, explicit kick-off, task preparation, task-start handoff, deterministic task-control admission, bounded execution, validation, and completion decision.

The accepted target remains a target rather than current architecture. Current `as-is.md` records and current contracts remain authoritative until separately authorized implementation is validated and the applicable records are deliberately updated.

Alternate-family review belongs only to the transitional provenance of the design and focused parallel-child clarification. It is not a permanent target-system lifecycle gate, role requirement, approval mechanism, or adoption criterion.

## Human orientation

The original rearchitecture is a program, not one sibling-parallelism feature. The immediate executable plan for plan admission, reservations, safe child concurrency, child-owned mechanical integration, and parent closure is one first-slice workstream inside that program. This roadmap places that workstream alongside the broader lifecycle, role, record, setup, migration, and evaluation work required by the accepted target.

The practical sequence is:

```text
accepted target envelope
  → overall realization roadmap
  → bounded detail plans and decisions
  → separately admitted implementation workstreams
  → repository-local candidate proof
  → setup-inclusive benchmark
  → migration and compatibility review
  → explicit advancement, target-adoption, and merge decisions
```

A benchmark is not the same as implementation completion, target adoption, or merge authorization. It is evidence for a bounded candidate workflow under a pre-registered protocol.

## Workstreams and dependencies

The program is divided into workstreams. A workstream is a bounded family of related changes and evidence, not an automatic task or blanket authorization.

### Workstream A — Design governance and representation

**Purpose:** Make the accepted target understandable, attributable, revisioned, and distinguishable from current architecture.

**Scope:** Design package structure; current-versus-target labels; component-anchor links; accepted-envelope identity; human-facing views; unresolved-question classification; decision and migration ledgers; lifecycle status vocabulary.

**Entry conditions:** Draft 11 acceptance remains the controlling envelope; the root and affected component anchors are available; no proposed record change silently rewrites current authority.

**Exit evidence:** A reviewed detail plan identifies exact records, consumers, fields or sections, compatibility behavior, protected inputs, validation, recovery, and the point where Human Review would be required for a material envelope change. A representative design artifact can be traced from its target package to each affected `as-is.md` anchor.

**Ownership boundary:** The design/record owner defines representation and links; task-control owns task-state authority; the orchestrator owns lifecycle decisions within scope; no document collection or skill acquires task authority merely by storing a plan.

**Stop conditions:** Missing or contradictory anchor; unclear current authority; a proposed representation changes goal, boundary, authority, acceptance, risk, protected input, or permitted external effect; known consumers cannot be bounded; or the change would silently adopt a target contract.

### Workstream B — Lifecycle, orchestration, and authority

**Purpose:** Realize the three-phase lifecycle and separate proposal, Human Review, kick-off, task preparation, admission, execution, validation, adoption, and merge.

**Scope:** Project-facing orchestration; design/prototyping interaction; decision presentation; escalation; task-start handoff; authority matrix; human status and progressive disclosure; feedback routing back to design.

**Entry conditions:** Workstream A has supplied the necessary identity and status representation; current `as-is` routing and task-control boundaries are preserved until compatibility evidence exists.

**Exit evidence:** A bounded workflow can demonstrate each transition with an attributable record, fail-closed missing authority, explicit next action, and no inference of approval from review, process exit, telemetry, or benchmark score.

**Ownership boundary:** The orchestrator manages lifecycle and escalates; the human decides material envelope changes and kick-off/adoption/merge decisions; task management creates task authority; deterministic task-control admits exact tasks; builders implement only admitted work.

**Stop conditions:** A transition conflates review with authorization; a caller cannot identify the decision holder; feedback would silently change an active task; or an unresolved question is blocking and has no owner or safe checkpoint.

### Workstream C — Agent roster, skill composition, and capability admission

**Purpose:** Adapt purpose-based roles and reusable procedures without treating model names, skills, or telemetry as authority.

**Scope:** Root orchestrator, design/prototyping role, parent and child component-builders, evidence validator, optional specialist, master skill compositions, capability declarations, host admission, and compatibility with retained skills.

**Entry conditions:** Workstream B defines lifecycle ownership and Workstream A defines role/record relationships; consumer inventory identifies current users before replacement or retirement.

**Exit evidence:** Role contracts, skill compositions, capability requirements, and migration dispositions are reviewed; one composition is exercised with current paths retained; denied or missing capabilities fail closed; model substitution does not alter authority.

**Ownership boundary:** Agents own workflow decisions within scope; skills provide procedures only; tools perform operations; task-control and host profiles govern admission. No skill grants a tool or permission.

**Stop conditions:** A role has no clear owner; a skill becomes an implicit authority boundary; a replacement lacks consumer evidence; an unavailable capability would be silently substituted; or a model identity is treated as a permanent role.

### Workstream D — Implementation packets and assurance

**Purpose:** Turn accepted design into detailed instructions that permit substantially blind execution while preserving safety, evidence, and escalation.

**Scope:** Packet schema/content; plan injection; protected inputs; allowed and prohibited paths; capabilities; ordered instructions; dependencies; acceptance; validation; budget; recovery; conflict handling; child handoffs; evidence review; unresolved-question handling.

**Entry conditions:** Workstreams A–C provide identity, authority, role, and capability facts; the implementation scope and owner are bounded; the packet does not require the child to make a material design choice.

**Exit evidence:** An exact packet is reviewed and admitted; a fresh child follows it without unrelated discovery; negative tests show scope, protected-input, missing-dependency, contradiction, budget, and validation failures stop safely; evidence is attributable and complete.

**Ownership boundary:** The parent prepares child plans as part of its one bounded task; the child owns local implementation and validation; assurance checks evidence; task-control admits; the child cannot edit parent authority or sibling scope.

**Stop conditions:** Packet ambiguity changes acceptance or ownership; protected controls are not enforceable or auditable for the risk; required validation is unavailable; or child and parent evidence cannot be separated.

### Workstream E — First execution-control slice

**Purpose:** Prove the minimum runtime structures required for safe parent/child candidate execution.

**Scope:** Frozen draft 6: plan admission, parent allocation and per-component reservations, independent-child admission, invalidation and recoverable stopping, queued freshness, child-owned mechanical integration, protected-input/scope checks, lock/recovery behavior, parent closure evaluation, and candidate fixture harness.

**Entry conditions:** Human Review accepts the exact draft 6 plan; separate kick-off names the first bounded implementation slice; the process-adapter boundary is resolved; task preparation and exact task-control admission complete.

**Exit evidence:** Pure decision, reservation, process-adapter, regression, and candidate-fixture checks pass; candidate scenarios execute through the new structures; baseline behavior remains intact; residual risk and recovery evidence are recorded.

**Ownership boundary:** Task-control owns admission/reservations/closure facts; the process adapter owns mechanical host application; the child owns semantic implementation/validation/integration decision; the parent owns planning and descendant accounting; the fixture owns evidence harnesses.

**Stop conditions:** Atomicity cannot be proven; protected inputs can change; stale or conflicting integration can partially apply; process-adapter ownership is unresolved; parent success can hide a child; or candidate evidence is obtained through baseline-only paths.

**Relationship:** This is the first-slice workstream, not the program. It is necessary but insufficient for the full target.

### Workstream F — Host, setup, consumption, and isolation

**Purpose:** Establish what can safely be consumed outside the immediate repository and state honest isolation limits.

**Scope:** Host-neutral resources; adapters; setup discovery and wiring; project-local records/state; candidate and baseline directories; configuration preservation; provider and credential boundaries; filesystem/network/process isolation claims.

**Entry conditions:** Workstream C defines capability needs; Workstream E provides a candidate flow; a separately owned mock consumer and protected seed are available.

**Exit evidence:** Repository-local setup and mock-consumer proof pass with no unrelated configuration overwrite; candidate and baseline are isolated by separate locations; claims are limited to demonstrated controls; unsupported installation, portability, upgrade, downgrade, uninstall, and untrusted-project claims remain deferred.

**Ownership boundary:** Host/setup owner owns setup and adapter behavior; consuming project owns project-local state and policy; providers/credentials remain environmental; workers do not gain broader access from setup.

**Stop conditions:** Setup overwrites unrelated state; project-local state leaks across candidates; provider or credential use is required unexpectedly; or a prompt/worktree-only boundary is presented as strong isolation.

### Workstream G — Migration, compatibility, and recovery

**Purpose:** Move proven consumers incrementally while retaining current behavior and preserving reversal.

**Scope:** Current-consumer inventory; source-to-target migration ledger; compatibility adapters; staged rollout; dual-path retention; recovery checkpoints; artifact deprecation/replacement/drop; merge-target freshness.

**Entry conditions:** At least one candidate path has passed evidence review; source consumers and owners are known; target behavior is not merely inferred from tests or benchmark rank.

**Exit evidence:** Each migrated consumer has before/after behavior evidence, an owner, compatibility path, recovery option, and removal gate; no source artifact is retired while an unaccounted consumer or recoverable uncommitted state remains.

**Ownership boundary:** Migration owner coordinates source-to-target mapping; component owners update their records and implementation; the orchestrator resolves cross-component decisions; the human approves material adoption or retirement.

**Stop conditions:** Consumer inventory is incomplete for the affected boundary; candidate and source behavior diverge without an approved decision; recovery is unavailable; or the post-benchmark merge target differs from the evaluated revision.

### Workstream H — Evaluation and advancement

**Purpose:** Measure the candidate workflow against the current workflow under controlled, setup-inclusive conditions.

**Scope:** Separate mock consumer; common seed; pinned `master` baseline; candidate revision; feature; setup; model/budget/retry settings; validators; protected scorer; rubric; safety policy; thresholds; advancement rule; report.

**Entry conditions:** Workstreams E and F have produced candidate behavior and setup evidence; Workstream G has identified the merge and migration scope; the benchmark protocol is separately reviewed and approved.

**Exit evidence:** Baseline and candidate runs complete under equivalent conditions; all outputs are retained with revision identity; safety-critical failures are reported; bounded claims are independently reviewed; the advancement decision is explicit and does not imply automatic adoption or merge.

**Ownership boundary:** Evaluation owner controls seed, protocol, scorer, and reporting; workers cannot alter protected evaluation inputs; the human decides advancement and later adoption; merge authority remains separate.

**Stop conditions:** Candidate behavior is absent; baseline/candidate conditions are inequivalent; scorer or validator is mutable by the worker; setup effects are omitted; a safety or authority failure occurs; or thresholds/advancement rules were changed after seeing results.

## Dependency and sequencing model

The workstreams are staged, but not necessarily all serial. Planning and detail-plan preparation can proceed in parallel when they do not change one another's inputs. Implementation and evidence gates remain ordered.

```text
A Design governance and representation
  └─→ B Lifecycle/orchestration/authority
       ├─→ C Agent/skill/capability composition
       └─→ D Implementation packets and assurance
            └─→ E First execution-control slice
                 └─→ F Host/setup/consumption proof
                      └─→ G Migration/compatibility closure
                           └─→ H Approved benchmark and advancement
                                └─→ I Target adoption and merge decision
```

The focused draft 6 workstream can be implemented once its own Human Review, kick-off, process-adapter boundary, task preparation, and task-control admission gates pass. It must consume stable enough identity, authority, and packet facts from A–D; if it exposes a material gap, the affected path stops rather than inventing a contract. F, G, and H depend on actual candidate behavior and cannot be claimed from plans or baseline tests.

## Phase gates

### Gate 0 — Roadmap and coverage alignment

**Purpose:** Confirm that the program plan covers the accepted envelope and that draft 6 is correctly positioned as a first slice.

**Required evidence:** This roadmap, its exact revision identity, review records, a coverage map, explicit exclusions, owner roles, dependency graph, and unresolved-question ledger.

**Decision:** Human Review may accept, request revision, defer, or reject this roadmap. Acceptance authorizes no task, kick-off, implementation, benchmark, adoption, or merge.

**Exit:** A set of bounded detail-plan candidates exists and the first-slice relationship is unambiguous.

### Gate 1 — Detail-plan closure and executable packet preparation

**Purpose:** Convert each required workstream into bounded, anchor-linked implementation plans without silently changing the accepted envelope.

**Required evidence:** Reviewed detail plans for each selected workstream; exact component ownership; task decomposition; protected inputs; acceptance; validation; recovery; dependencies; unresolved-question dispositions; and compatibility/migration mapping.

**Decision:** Separate Human Review is required for any material successor envelope. Planning closure is not task authority.

**Exit:** The orchestrator can name the first implementation slice and its exact owner, while later work remains visibly planned, deferred, or blocked.

### Gate 2 — Kick-off, task preparation, and admission

**Purpose:** Authorize and admit one bounded implementation slice.

**Required evidence:** User kick-off for the named slice; pre-task ownership decisions; exact task records; task-start handoff; worker/capability facts; budgets; protected controls; and deterministic task-control admission.

**Decision:** Kick-off is limited to the named slice. Task-control admission is mechanical readiness, not semantic approval or target adoption.

**Exit:** Only admitted tasks may begin. Unadmitted work remains untouched.

### Gate 3 — Candidate structure readiness

**Purpose:** Build and validate the structures needed for candidate execution before using the pilot as candidate evidence.

**Required evidence:** Workstream E focused checks; relevant regression checks; process-adapter boundary evidence; atomic reservation and recovery evidence; protected-input and scope evidence; and a preserved recovery surface.

**Decision:** The orchestrator may permit candidate-flow testing only when the required checks pass. A failed structure blocks dependent scenarios.

**Exit:** Candidate structures exist at a recorded revision and are ready for the fixture harness.

### Gate 4 — Repository-local candidate proof

**Purpose:** Exercise the target workflow on a controlled repository-local slice.

**Required evidence:** Candidate fixture scenarios through the new path; a separately owned mock consumer; setup evidence; baseline regression; structured child handoffs; integration and closure evidence; and residual-risk record.

**Decision:** Evidence review determines whether bounded candidate claims are supported. It does not adopt the target or authorize benchmarking automatically.

**Exit:** A candidate revision, proof report, and unresolved-risk disposition exist.

### Gate 5 — Benchmark protocol approval and execution

**Purpose:** Compare current and candidate workflows fairly, including setup.

**Required evidence before execution:** Seed identity; pinned baseline `master` revision; candidate revision; feature; setup conditions; equivalent settings; budget/retry policy; deterministic checks; protected validator/scorer; rubric; safety-failure policy; thresholds; advancement rule; and reporting format.

**Decision:** The user separately approves the exact benchmark protocol and advancement rule. Benchmark execution remains a bounded evaluation action, not automatic adoption.

**Exit:** Reproducible baseline and candidate results with safety and limitation reporting, followed by an evidence review.

### Gate 6 — Advancement, adoption, and merge

**Purpose:** Decide whether the candidate should become the accepted implementation and whether a scoped branch integration is safe.

**Required evidence:** Benchmark evidence supports only its pre-registered bounded claims; compatibility and migration closure exists for the proposed merge scope; current behavior and consumers are accounted for; target records can be updated deliberately; the merge target is the same or a freshly validated revision; no protected or unrelated changes are included; and recovery/reversal remains available.

**Decisions:** These are separate decisions: (1) candidate advancement, (2) target-contract adoption/current-record update, and (3) merge authorization. A human may approve one without approving the others.

**Exit:** Only explicit approval of the exact merge scope permits integration into `master`. If approval is withheld, the candidate remains a branch/recovery artifact and no source behavior is retired.

## Detailed first-slice placement

The frozen executable realization plan at `drafts/agentic-development-system-executable-realization-plan-draft6.md` is the concrete plan for Workstream E. It covers the structures and scenarios needed to prove safe parent/child execution:

- deterministic plan readiness and admission;
- parent allocation and atomic per-component reservation;
- independent-child concurrency and conservative overlap handling;
- dependency invalidation with recoverable stopping;
- queue/dequeue freshness checks;
- child-owned semantic decision followed by host-side mechanical application;
- scope, protected-input, stale-base, dirty-target, conflict, lock, and recovery handling;
- parent closure only after child terminal disposition, validation, integration evidence, and accounting; and
- provider-free candidate fixture tests after the structures pass focused checks.

It does not implement the design lifecycle, complete record model, full role and skill migration, setup/consumption, broad isolation, migration ledger execution, or benchmark. Those remain in Workstreams A–D and F–H. Draft 6 should therefore be presented and evaluated as a prerequisite candidate-control slice, not as completion of the program.

## Benchmark and merge answer

### Earliest defensible benchmark point

The earliest defensible benchmark is after Gate 4 and Gate 5 preparation, not after merely merging draft 6's code or passing existing fixture tests. Specifically, the branch must have:

1. completed the reviewed detail planning needed for the selected candidate flow;
2. implemented the required candidate structures and their focused tests;
3. resolved the process-adapter ownership boundary;
4. exercised the candidate path through a repository-local proof harness;
5. retained passing baseline regression evidence;
6. produced a separately owned mock consumer and setup-inclusive run path;
7. frozen the candidate revision and pinned the `master` baseline revision;
8. defined equivalent settings and protected evaluation controls; and
9. received separate approval for the exact benchmark protocol and advancement rule.

At that point, the branch is benchmarkable as a **candidate pilot workflow**. It is not yet evidence that the full accepted rearchitecture has been realized.

### Earliest defensible merge point

The earliest defensible merge with `master` is after benchmark evidence review and Gate 6, when:

- the benchmark's bounded advancement criteria are met with no safety-critical or authority failure;
- all claims are limited to the tested candidate scope;
- the exact merge scope has a consumer-backed migration and compatibility plan;
- current behavior remains available where migration is incomplete;
- changed agents, skills, adapters, records, and workflows have source-to-target dispositions;
- the branch is rebased or otherwise validated against the actual merge-target revision after evaluation;
- focused, regression, setup, and candidate tests pass on that merge target;
- protected evaluation inputs and unrelated changes remain untouched;
- recovery and reversal are recorded; and
- the human separately approves target adoption and the exact merge.

A compatible, opt-in infrastructure slice may be merged earlier only as a separately authorized exception. Such a merge is not adoption of the whole target design and must not be described as proof that the full rearchitecture is complete.

## What must not be inferred

- Passing current fixture tests does not prove the candidate structures exist.
- Passing candidate-control tests does not prove the full target workflow exists.
- A successful repository-local proof does not prove provider efficacy, portability, strong security isolation, installation, upgrades, downgrades, uninstall, or multi-project production readiness.
- A benchmark result does not automatically authorize target adoption, artifact retirement, or merge.
- A clean branch does not prove consumer compatibility.
- A child commit, process exit, registry event, trace event, or model output does not prove task completion.
- An alternate-family review does not become a permanent target-system gate.
- A merge into `master` does not itself prove all future target phases are complete.

## Explicit exclusions and residual risks

This roadmap does not authorize or promise:

- implementation of any workstream;
- wholesale replacement of current skills, agents, adapters, or records;
- automatic target-contract adoption from passing tests or benchmark results;
- provider-backed efficacy, external installation, distribution, upgrade, downgrade, uninstall, portability, or multi-project production isolation;
- complete filesystem, network, credential, process, or untrusted-project isolation without enforced controls and separate evidence;
- content-generation or general-task workflows in the first pilot;
- alternate-family review as a permanent target requirement; or
- merge simply because the branch is green or ahead of `master`.

Residual risks include incomplete consumer discovery, compatibility gaps, host isolation weakness, prompt-guided context leakage, approximate cost accounting, benchmark sensitivity to feature and settings, human cognitive overload, migration duplication, merge-target drift, and loss of recovery value if artifact-retirement checks are incomplete. These risks require explicit evidence and disposition at the affected gate; they are not solved by this roadmap.
