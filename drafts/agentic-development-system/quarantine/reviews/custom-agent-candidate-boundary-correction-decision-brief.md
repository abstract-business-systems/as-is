# Custom-agent candidate-boundary correction — decision brief

## Purpose

Record the current user's correction: planning must not fall back to using the existing implementation as the candidate merely because custom agents are named as its authors.

This decision brief preserves the correction without changing any frozen predecessor, current component, task, contract, launcher, or agent artifact. It is not a candidate-architecture packet, implementation packet, task record, kick-off, model selection, or implementation authorization.

`startsWork: false`

## Corrected interpretation

The Human Review-accepted construction-agent/model-binding Draft 1 establishes only that custom model-bound agents are the intended construction path. It does **not** authorize the following inference:

> A custom agent may implement the candidate by adding files to, extending, or treating the existing component-builder, task-control, control-plane, budget, launcher, task-record, adapter, or fixture implementation as the candidate system.

That inference would relabel the current implementation rather than construct and prove a candidate. It is rejected.

| Layer | Permitted role | Not permitted |
| --- | --- | --- |
| Custom construction agents | Plan, implement, validate, and review a separately defined candidate after their exact gate-time selections and authorizations | Serve only as alternative authors of extensions to the current implementation, then present those extensions as a new candidate system |
| Current repository implementation | Remain preserved current architecture; provide only minimum bootstrap governance where separately authorized; later serve as the benchmark baseline | Supply the candidate admission, reservation, recovery, closure, agent, skill, launcher, or integration mechanism by relabelling existing behavior |
| Current durable records | Preserve current authority and the minimum administrative evidence needed to govern planning | Become candidate contracts, candidate state, or evidence that candidate behavior exists |
| Candidate validation | Inspect the independently defined candidate through its own deterministic controls and provider-free proof boundary | Treat current tests or a current control-plane preflight as candidate proof |

## Candidate containment decision

The candidate is constructed on the current branch, `implementing-composable-skills`. That branch is the candidate and recovery/reversal boundary for this exercise. The later benchmark obtains the older implementation from a pinned `master` revision; it does not treat `master` as implementation authority or an approval source.

The benchmark must use a separate checkout or worktree for pinned `master` so checking out baseline behavior cannot overwrite, mix with, or silently replace candidate-branch work. No baseline checkout is authorized by this decision, and no comparison may run before the candidate is independently proven and separately approved for benchmarking.

## Consequence for current planning

No first-slice implementation packet is active or eligible for preparation from executable realization Plan Draft 6 alone. Its proposed task-control locations and current-component decomposition may remain historical planning provenance, but they cannot select the candidate's implementation location, ownership, or mechanism.

The cancelled root-to-task-control task preparation remains cancelled and is not a reusable template for the candidate. No current agent or component is a substitute for the separately defined custom candidate boundary on the current branch.

## Required successor decision

Before selecting workers, profile files, model routes, capabilities, budgets, validators, task records, or implementation artifacts, create a separate candidate-boundary architecture packet. The packet must define and distinguish:

1. the candidate's independently realized architecture and entry points on `implementing-composable-skills`;
2. the candidate's custom-agent contracts, live communication, task/admission semantics, state, validation, recovery, and integration mechanisms;
3. the exact permitted bootstrap interactions with current governance, with evidence that they do not become candidate behavior;
4. the separation of candidate code, candidate tests, and candidate evidence from current implementation and baseline tests;
5. how later equivalence/benchmark work uses a pinned `master` checkout or worktree to compare the preserved current workflow with the independently proven candidate; and
6. the migration/adoption boundary, which remains outside the candidate construction and proof scope.

The packet must not assign a candidate artifact namespace, component owner, model, provider route, holder, capability, budget, or task by assumption. Those are later bounded decisions supported by the packet and its reviews. A missing fact blocks the affected transition; it does not permit a fallback to the current implementation.
