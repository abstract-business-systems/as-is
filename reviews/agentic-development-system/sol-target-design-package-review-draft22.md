# Sol review of target-design package draft-22

This advisory, read-only review assessed the exact package snapshot at `drafts/agentic-development-system-target-design/` against the canonical handoff, current records, repository instructions, the non-authoritative composable-skills proposal, and prior Terra/Sol reports. It does not adopt target contracts, create tasks, authorize implementation, or approve user presentation.

## Verdict

**Revise — not ready for the Grok gate.** The package has strong control-boundary and evaluation structure, but the frozen revision is internally inconsistent and several exact review contracts remain underspecified.

## Strengths

- The ledger supports 24 reusable proposal headings plus four new reusable additions and 12 master headings plus two new master additions, with unique target identifiers.
- Design facilitation is workflow-only through `thinking-companion`; no separate design-facilitation agent target remains.
- Setup has one explicit resource/action matrix covering seed, copies, controls, manifests, results, and runtime state.
- Current/planned separation, Path A, protected controls, fail-closed intent, both sides of paired runs, case/dimension results, weighted scoring, and recovery concepts are present.
- The first slice appropriately excludes credentials, external effects, distribution, package installation, security isolation, and multi-project claims.
- Prior incomplete Grok evidence is preserved rather than treated as approval.

## Blocking issues

1. The manifest identifies `target-design-v1-draft-22`, while the non-manifest package files still identify draft-21. The digest table therefore cannot describe one exact package snapshot.
2. SHA-256 values must be regenerated after revision normalization; this review could not independently recompute them through its read-only inspection surface.
3. `comparison-manifest-v1` still needs a closed protected-input ID registry, exact nested object schemas, canonical digest/unavailable representation, and unambiguous terminal invalidation semantics.
4. The cell/result contract needs exact predicate-result structure and a deterministic aggregation equation for side, run, case, and dimension, including missing, extra, blocked, unknown, invalidated, and disagreement states.
5. The affected-record inventory needs an explicit universe and complete one-path-per-row affected/excluded lists; currently it mixes records, source artifacts, and a nonexistent canonical record.
6. The architecture diagram should visibly include package freeze/verification, Grok provenance/trial, Terra reconciliation, final Sol review, and hard fail-closed admission prerequisites.
7. The Grok trial record must be aligned to the current package, distinguish every prior attempt, and record provenance, packet identity, exact bounds, result shape, and human outcome before the gate can pass.

## Required next revisions

- Normalize all package files to one new revision after draft-22.
- Split affected records, explicit exclusions, and non-record fixture sources; enumerate affected live skill records and referenced current records.
- Add exact manifest protected-input IDs/object schemas, status/invalidation rules, and cell predicate/result schemas.
- Make the scoring and repetition procedure fully deterministic, including baseline/candidate side handling and review-burden evidence.
- Complete the architecture diagram gates and normalize the Grok trial record.
- Recalculate the manifest digests and rerun the consistency audit before another fresh Sol review.

## Residual uncertainty

Feature, seed, baseline/candidate revisions, human holders, final rubric approval, runtime enforcement, Grok provenance, external consumption, and implementation remain unresolved. This verdict is advisory and does not authorize Grok invocation, presentation, task creation, adoption, or implementation.
