# Task-Facing Tools Readiness

## Purpose

Record the smallest evidence-backed boundary for future agent-facing task tools without creating `tools/task/`, registering a new tool, or changing runtime behavior. The current task-control APIs remain authoritative and direct callers remain the recovery path.

## Current Decision

**Do not create `tools/task/` now.** Current evidence shows no focused task-tool consumer or registration route that requires a separate sibling family. Structural similarity to context or evidence tools, or one status operation alone, is insufficient. Reconsider only after at least two concrete role-admitted agent-facing consumers share bounded request/result needs that cannot safely remain direct task-control or orchestrator callers. Preserve direct callers and current registration unchanged until that gate is met.

## Smallest Future Seam

If the two-consumer gate is later met, begin with read-only durable-record-backed observations only:

- task summary/status and bounded progress;
- open durable questions, blockers, and approval-wait state;
- source-labelled budget and next-check-in observations; and
- bounded completion-eligibility and descendant-closure facts.

The future tool must replace current relative `path` fields with opaque task references or approved logical component identifiers before emission. It must not expose task-record, component, worktree, session, log, or configured-directory paths. It must not infer authority from host health, process exit, telemetry, or a missing private artifact.

Do not include generic mutation controls in the initial seam. If later evidence justifies a control operation, each operation must route to the corresponding `ControlPlane` method, pass the current durable revision/freshness marker, reread before mutation, fail closed on mismatch, and preserve approval, cancellation, descendant, budget, and completion authority. The tool must never edit records directly, calculate authorization independently, infer completion, or turn a tool result into approval.

The current `ControlPlane` APIs do not accept a record-revision/freshness argument for these operations. That is a future adapter seam requirement, not evidence that current task-control already implements stale-write rejection. The execution-contract stale-result rule therefore remains a future implementation fixture and must not be claimed as current task-tool behavior.

## Compatibility And Recovery

The current direct control-plane callers, task records, role declarations, and context/evidence/agent registration surfaces remain authoritative and unchanged. The future task-tool candidate is failed when the two-consumer gate is absent, output bounds or path privacy are unproven, stale revision handling is missing, mutation routing is ambiguous, or admission/recovery evidence is contradictory. Remove only candidate task-tool artifacts and restore direct control-plane callers and current registration; do not create a compatibility directory or alter task authority.

## Non-Authorizations

This readiness record does not authorize `tools/task/`, new tool registration, task-schema changes, control-plane redesign, direct record edits by tools, role substitution, budget/approval/cancellation/completion authority transfer, Pi or process changes, path-emission implementation, target writes, external services, or broad tools/modules regrouping.
